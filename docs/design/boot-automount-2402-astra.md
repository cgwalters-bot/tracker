# /boot automount ownership: design for bootc #2402

## Mechanism

Source inspection, 4 November 2026; references pin the three read-only clones. No VM reproduction was run. Tracker #1244 and upstream #2402 are reports, not proof of every configuration.

OSTree's `boot_mount_generator()` emits a normal-priority `boot.mount` binding `/sysroot/boot` when `boot/loader` is a symlink, `/boot` exists, and fstab does not own `/boot`. This is not composefs-only. GPT-auto emits lower-priority mount **and automount** units: overriding its `boot.mount` does not override `boot.automount`. Its 120-second expiry queues a stop job for the effective mount, hence can unmount OSTree's bind. Already-mounted paths are deliberately **not** “busy” to GPT-auto, so mounting earlier is not a reliable exclusion. [O1, S1–S3]

OSTree #3608's volatile-root symlink restores physical-disk discovery obscured by composefs. It exposes this collision; it did not introduce automounting. GPT-auto also processes loader partitions on BIOS boots, skipping the EFI UUID check there. On UEFI, loader UUID matching matters; fstab entries anywhere under `/boot` or `/efi` suppress loader-partition generation in current systemd. XBOOTLDR independently claims `/boot`. [O2, S4]

OSTree opens `boot` relative to its default sysroot `/`, and explicitly remounts `/boot` writable. An expired mount can therefore break reads or finalization. However, “autofs doesn't service private namespaces” is too broad: bootc #2411 changed re-exec to `--propagation=slave`, allowing host mounts inward. That does not resolve competing ownership. Current native-composefs bootc also holds `/boot` open during staging and distinguishes a separate boot filesystem from physical-root boot storage (#2440); those are not equivalent to fixing OSTree's path. [O3, B1–B3]

The reported EPERM/EINVAL are not independently reproduced here. “Silently dropped” needs qualification: OSTree removes staged runstate before part of finalization, returns errors, attempts a failure stamp, and boot-complete reports that stamp next boot. Failure to open/write boot can defeat that persistence. The old deployment remaining selected is plausible, not evidence that all failures delete the deployment itself. [O4]

## Options

### A. Prefer an existing /efi again; opt images in

The concrete failure to prevent is an ESP automount expiring an unrelated `/boot` bind. Restore existing-directory `/efi` preference, not a blanket automount disable. This convention arrived in **v232**; **v252** has it. Commit `6a488fa7cc` reversed preference for **v254**; **v257, v258 and inspected HEAD** prefer `/boot`. Thus shipping an empty `/efi` alone does not fix current systemd. [S5]

Change systemd's ESP path selection and tests, then selected base images to provide `/efi` before generators run. No OSTree/bootc API change. Keep behavior unchanged when `/efi` is absent: opt-in by image layout, no new switch or runtime probing loop. However, existing `/efi` directories also activate this policy: it changes placement on non-OSTree systems too. The v254 reversal intentionally preferred `/boot` for BLS compatibility; upstream must accept that trade-off or this direction cannot proceed. Preserve fstab precedence and XBOOTLDR handling.

Works for the reported BIOS-plus-ESP case and eligible UEFI systems, with or without composefs. Separate `/boot` explicitly configured in fstab remains untouched; XBOOTLDR without fstab still automounts `/boot`, so this is **not a universal fix**. FCOS/RHCOS separate-boot generators must be tested, not assumed equivalent to fstab. Fedora bootc and CentOS Stream 10 need their shipped systemd builds/backports checked; upstream version alone does not establish vendor behavior.

Deploy systemd support and the directory together; reboot required, not merely daemon-reload. Rollback to old `/boot`-first systemd reintroduces the fault. Backport to supported rollback images before claiming fleet safety. Do not move ESP contents or remove old bootloader paths. CI: common matrix below, plus `/efi` absent/empty/nonempty, explicit ESP fstab and XBOOTLDR; verify no unexpected path migration.

### B. Remove the bind and use physical-root boot storage

This is a larger migration, not a simple revert. The original 2015 bind commit ensured runtime bootloader configuration access on single-partition systems. #3571 later moved it into the generator to survive bare and staged soft reboot; reverting that move merely restores the old bind and loses soft-reboot support. [O5]

OSTree needs one boot-directory resolver for booted versus offline sysroots, remounting, BLS writes, finalize and boot-complete. Bootc already demonstrates why “always `/sysroot/boot`” is wrong: a separate filesystem may exist only at `/boot`. Audit GRUB scripts, rpm-ostree callers and admin tools expecting `/boot`; GRUB computes kernel prefixes from device identity. [O3–O6, B2]

BIOS/UEFI and composefs/non-composefs need identical storage semantics. FCOS/RHCOS separate partitions cannot switch paths without mount-layout coordination; Fedora bootc and Stream 10 single-partition layouts are easier but external `/boot` consumers still break. Changes span OSTree, bootc, image integration and potentially rpm-ostree/GRUB tooling; no systemd change inherently required. Keep readers compatible across upgrade and rollback before changing mounts; never migrate BLS data irreversibly. CI: common matrix plus offline `ostree admin`, rpm-ostree updates, GRUB regeneration, BLS/kernel path checks and interrupted finalization. Defer: too broad for the first repair.

### C. Explicit fstab ownership of the existing bind

For diagnosed single-partition hosts, declare the actual `/sysroot/boot` → `/boot` bind in fstab, without `x-systemd.automount`. This uses GPT-auto's supported exclusion, rather than masking its output. OSTree #3654 already yields to fstab. Do not add a dummy entry: fstab should describe the real mount. [O1, S4]

This can work on BIOS/UEFI and either root implementation; separate-boot hosts instead retain their actual filesystem entry. It needs layout-specific installer/image configuration, not a generic base-image line. Existing deployments need careful `/etc` merging; old OSTree lacking #3654 can collide on rollback. Preserve soft-reboot ordering/default-dependency semantics of the existing unit. Suppressing ESP discovery also requires explicit ESP access where needed. Changes are small per layout, but fleet migration is not. CI: common matrix plus modified fstab, rollback before #3654, separate boot and soft reboot. Useful targeted mitigation, not preferred generic repair.

Ordering alone and `RequiresMountsFor` help individual services, not shell callers or ownership. Explicit fstab `x-systemd.automount` ownership has idle expiry **disabled by default**, unlike GPT-auto's 120 seconds; it could avoid expiry but retains demand-mounting/shutdown risks. Prefer the eager bind for C. Disabling all GPT-auto discovery repeats #3608's broad blast radius; ESP's GPT no-auto flag is ignored. [S6–S7]

## Recommendation

Proceed with **A**, explicitly scoped to ESP-versus-bind collisions; do not remove `/boot` compatibility or revive the rejected masking approach.

1. First PR: systemd only, restore preference for an existing usable `/efi` in `add_partition_esp()`, with focused generator tests. Leave absent-directory behavior, fstab checks and XBOOTLDR unchanged. No new option or disk-format change. Include a conventional non-OSTree upgrade case with both directories already present: verify kernel/BLS installation and bootloader consumers after ESP placement changes; gate acceptance on that compatibility result.
2. Before image rollout, run a tmt regression through bootc's bcvk-backed VM runner. Cross BIOS/UEFI, single/separate `/boot`, composefs on/off; cover Fedora bootc, CentOS Stream 10 and FCOS, with RHCOS qualification downstream. Use a failing old-image control. [B4]
3. Bound each case to ten minutes: observe mountinfo/unit origins without touching `/boot`, allow up to 180 seconds for idle expiry, run status, upgrade and updater service, then idle again and reboot. Assert the new deployment actually booted and finalize/boot-complete succeeded. Exercise rollback and bare/staged soft reboot. Record package versions, fstab and partition types. This is a proposed CI plan, not passing evidence.
4. Only then pair image `/efi` provisioning with systemd backports and rollback coverage. Track XBOOTLDR and separately generated boot mounts as explicit remaining cases, not silently included successes.

Draft upstream issue text (not posted):

> The collision remains distinct from namespace propagation: GPT-auto's automount can expire OSTree's winning bind mount. Existing `/efi` preference disappeared in systemd v254, so adding that directory alone is insufficient on current releases. I propose a narrowly tested restoration of that opt-in convention, followed by paired image/backport rollout. This preserves `/boot` consumers but does not solve XBOOTLDR ownership. VM expiry, finalization and rollback tests are still needed; source inspection alone is not a reproduced fix.
