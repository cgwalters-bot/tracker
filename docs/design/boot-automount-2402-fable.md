## Mechanism

**Two generators, one path.** On a same-partition layout (`/sysroot/boot/loader` is a
symlink) with no `/boot` line in fstab, `ostree-system-generator` writes `boot.mount`,
a bind of `/sysroot/boot`, into the normal generator directory [1].
`systemd-gpt-auto-generator` dissects the root disk and, finding an ESP and no
XBOOTLDR partition, writes `boot.mount` and `boot.automount` (`TimeoutIdleSec=120`)
into the *late* directory [2][3]. The normal directory wins for `boot.mount`, so the
automount triggers ostree's bind. An automount is implicitly `Before=` its mount
[4]: the autofs trap goes on `/boot` first, the bind lands on top. After two idle
minutes the kernel reports expiry and systemd stops `boot.mount` [5]; from then on
`/boot` is a trap.

**Why `/boot` looks free.** gpt-auto skips only a populated path or a non-directory;
an empty directory is free, and so is an existing mount point, because generators
also run on `daemon-reload` [6]. The deployment's `/boot` must be empty [7]. Until
ostree v2026.1 the bind was made by `ostree-prepare-root`
in the initramfs, so `/boot` was already a mount point and `automount_start` refused
to start over it, with a logged error [8]. PR 3571 (`a88e66ea`, v2026.1) moved the
bind into the generator for soft-reboot [9]; PR 3487 only refactored it [10]. The
bind itself dates from 2015 (`598530da`), not from a recent PR.

**Why gpt-auto now finds the disk.** `blockdev_get_root` reads
`/run/systemd/volatile-root`, else stats `/` then `/usr` [11]. With composefs both are
overlays, so gpt-auto found nothing until PR 3608 (`62109dca`, v2026.3) made
`prepare-root` create the symlink [12]; bootc's initramfs already did so for its own
backend [13]. Without composefs, `/` is a bind with the physical `st_dev`, so those
systems were exposed from v2026.1. So the issue's claim holds for composefs:
v2026.1 removed the guard, v2026.3 widened the exposure.

**Which firmware.** On an EFI boot, gpt-auto mounts the ESP only when
`LoaderDevicePartUUID` names it or an XBOOTLDR partition; on a non-EFI boot it skips
that check [14]. GRUB
sets that variable only with its `bli` module, so the reporters (BIOS, hybrid
`to-disk` layout with an unused ESP [15]) are the main population. Whether Fedora's
signed GRUB loads `bli` decides if UEFI+GRUB is affected; the test plan checks it.

**`opendir(boot): EPERM`.** libostree opens `boot` relative to the sysroot fd [16].
bootc re-execs under `unshare -m`; the kernel refuses to trigger an autofs mount from
a foreign mount namespace with private propagation, with `EPERM` [37]. bootc PR 2411
switched to slave propagation so the trigger is honoured and the mount propagates
[17]; that fixes the symptom only in bootc's own process.

**Finalize failure.** `_ostree_sysroot_ensure_writable` remounts `/boot` read-write
[18]; `MS_REMOUNT` on a path that is not a mount root fails with `EINVAL`. So at
`ExecStop` time, inside the service's `ProtectHome` namespace [19], `/boot` was the
bare directory on the read-only root: the trap was already gone. The 2022 hold unit
[20] assumed a real device mount that systemd re-establishes on trigger; with an
expired bind the service exits non-zero, the staged deployment is dropped and the
reboot is a no-op. The shutdown ordering was not reproduced; the CI test pins it.

**Other corrections.** The composefs-native bootc backend already does direction 2:
it reads `/sysroot/boot` unless a separate `/boot` is mounted [21], mounts the ESP
by device at a temporary path [22], and holds `/boot` open while staged [23]; PR
2440 belongs there. systemd preferred an existing `/efi` in v232, dropped
that with XBOOTLDR in v242, and added the fstab `/boot` or `/efi` prefix opt-out in
v256 [24].

## Options

### 1. gpt-auto prefers `/efi` (operator direction 1)

Change `add_partition_esp` so an existing, unused `/efi` directory wins over an empty
`/boot` [3], restoring the v232 rule; base images ship `/efi`. `bootctl` already
searches `/efi` first [25] and bootupd lists it as a known ESP path [26].

- *Correctness.* BIOS and UEFI+GRUB: the ESP idles at `/efi`, harmless. Separate
  `/boot` (FCOS/RHCOS): ostree writes no bind [1]; FCOS deletes the gpt-auto
  generator at compose time [40], and bootc's separate-boot installs write a `/boot`
  fstab line [30] that systemd ≥256 honours [24]. A unit-mounted `/boot` with no
  fstab line is wrapped on every version (`Before=` [4] defeats the guard [8]);
  `/efi` does not help there. bootc
  UKI/systemd-boot: the ESP is found by device [22], so its automount path is
  irrelevant. ostree layouts with loader entries on an ESP mounted as `/boot` (the
  PR 3608 case) must not ship `/efi`. Composefs or not: identical. Fedora bootc and
  CentOS Stream 10 need backports (Fedora 44 ships 259, C10S 257).
- *Upgrade and rollback.* Pure image content; old deployments keep today's behaviour.
  No partition, fstab or karg edits. No ostree or bootc change.
- *Changes.* systemd: ~15 lines plus man page and NEWS. Base images: one directory.
  Fedora and C10S: backports. This won't help until they ship, so pair with option 3.
- *CI.* Below.

### 2. Drop the bind mount, always use `/sysroot/boot` (direction 2)

ostree would stop writing `boot.mount`, open `/sysroot/boot` when booted on a
same-partition layout, and adjust `RequiresMountsFor=/boot` in its units [20][27].

- *Correctness.* Every consumer of `/boot` must move: rpm-ostree units require it
  [28]; bootupd hard-codes `/boot/grub2` for BIOS and the static GRUB config [29];
  kdump, grubby, admin habits and docs. On BIOS the unused ESP would then be
  automounted at `/boot`, the opposite of what an admin expects.
- *Upgrade and rollback.* Old deployments still generate the bind, so new code must
  handle both shapes forever. Safe on rollback; hard to revert later.
- *Changes.* ostree (large), rpm-ostree, bootupd, docs. Months, several releases, no
  relief in the meantime. Not recommended.

### 3. Install-time fstab bind (uses two existing opt-outs)

`bootc install` already writes a `/boot` fstab line for a separate boot partition
[30]. For the same-partition layout it can write
`/sysroot/boot /boot none bind 0 0`: systemd ≥256 then generates no loader-partition
units [24], and ostree's generator yields to fstab (PR 3654) [31]: the documented
opt-out, decided where the layout is known.

- *Correctness.* Exact for new `to-disk` installs on any firmware, composefs or not.
  Must not be image content: it is wrong where the ESP really is `/boot`. RHEL 9
  (systemd 252) lacks the prefix rule but ships an older ostree.
- *Upgrade and rollback.* New installs only; `/etc/fstab` is merged per deployment,
  so rollback keeps it. Existing systems need option 1 or the manual line.
- *Changes.* bootc install: ~20 lines plus a test. Lands in days.

### Rejected

- **Partition flags.** The GPT no-auto bit is ignored for the ESP; the NoBlockIO
  bit is honoured but tells firmware not to expose the partition [32].
- **`systemd.gpt_auto=0` or `systemd.image_policy=` kargs.** Disables the DPS
  discovery bootc documents [33].
- **Masking or a `TimeoutIdleSec=0` drop-in from ostree's generator.** PR 3664's
  shape; rejected [38].
- **Non-empty `/boot` in the image** so gpt-auto picks `/efi` today: violates the
  bootc lint [7] and leans on an undocumented rule [6].

## Recommendation

Do option 1 as the durable fix and option 3 as the immediate one.

1. **First PR (bootc, lands quickly):** in `install.rs`, write the fstab bind line
   when there is no separate boot partition [30]; unit-test the fstab text; enable
   `switch_zstd_chunked` on ostree [34]. Document the line as the workaround for
   existing systems.
2. **systemd PR:** prefer an unused, existing `/efi` in `add_partition_esp` [3], with
   man page and NEWS; cite the v232 text [24] and `find-esp.c` [25]. Request Fedora
   and C10S backports.
3. **Base images:** add `/efi` to fedora-bootc and centos-bootc; FCOS has no
   gpt-auto generator and needs nothing.
4. **ostree:** no code change; close 3664.

**CI (bcvk/tmt).** Add a tmt plan booted with BIOS firmware (bootc's xtask only
passes `uefi-*` today [35]) on a fresh `to-disk` install: assert
`findmnt -t autofs /boot` fails, `boot.mount` is active, `bootc status` works after
`sleep 170` (systemd polls expiry every 40 s [5]) and after `umount /boot`, and a
staged upgrade survives reboot (reuse
`054-test-boot-automount.nu` [36] and ostree's kola `boot-automount.sh` [39]). On
the UEFI plan, record whether `LoaderDevicePartUUID` exists in efivars and, if so,
run the same assertions. For the systemd patch, boot with and without `/efi` and
assert the automount path.

**Draft text for bootc#2402 (operator posts):**

> Root cause, from source: since ostree 2026.1 the `/boot` bind is a generator unit
> instead of an initramfs mount, so `systemd-gpt-auto-generator` no longer sees
> `/boot` as taken and wraps it in an ESP automount; since 2026.3 that also happens
> with composefs because prepare-root now publishes the root device. On BIOS boots
> gpt-auto skips the `LoaderDevicePartUUID` check, so the unused ESP of a hybrid
> `to-disk` install is automounted on `/boot`, idles out after 120 s, and tears
> down the bind.
>
> Plan: (1) `bootc install to-disk` will write `/sysroot/boot /boot none bind 0 0`
> for same-partition layouts, which systemd ≥256 and ostree ≥2026.5 both honour as
> "hands off `/boot`"; existing systems can add that line today instead of masking
> `boot.automount`. (2) Upstream systemd: prefer an existing `/efi` directory for
> the ESP, as systemd 232 did; our base images will ship `/efi`. No ostree change.
