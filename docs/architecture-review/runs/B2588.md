**Design summary**

`bind_storage_roots` sets up each podman/skopeo child in its `pre_exec` hook. The child fchdirs into the bootc storage root, unshares a new mount namespace and bind-mounts "." onto `/run/bootc/storage` (`STORAGE_ALIAS_DIR`). The module comment already relied on the new namespace "automatically cleaning up the global bind mount". That only holds if the namespace does not propagate mounts back to its parent.

When the caller's `/` is shared, the bind leaks onto the host and stays there. The comment says this happens when `install ... --source-imgref` skips bootc's own unshare (issue 2455, which I did not read). The fix calls `mount_change("/", PRIVATE | REC)` after `unshare(NEWNS)` and before `mount_bind` (podstorage.rs:137-146). A new booted tmt test (number 63) and its generated plan make `/` rshared inside `run_install`'s namespace, run `install to-filesystem --source-imgref`, and assert with `findmnt` that `/run/bootc/storage` is not mounted.

Invariant (inferred): mounts created by a podman child for bootc storage, including the alias bind and any overlay mounts podman makes under it, never become visible in, or outlive the child in, the caller's namespace. The success path is fchdir, unshare, then make-rprivate, bind, fchdir back, exec podman. When the child exits, its namespace and all its mounts are freed.

**Defects**

None supported by the packet. The ordering is correct. Propagation is changed only inside the freshly unshared namespace, so the parent is not affected (AR-02, S-fd-h/S-style Destructors: the mount's lifetime now follows its owning namespace). The new step comes after `fchdir(&amp;storage_root)`, so the cwd-based bind source the existing comment depends on (lines 115-128) is not disturbed. The child already needed CAP_SYS_ADMIN for `unshare(NEWNS)`, so no new privilege is required. A failure returns `io::Error` from `pre_exec`, which surfaces as a spawn error to the existing caller and does not produce a second log report (AR-01, S-style Error Handling/Logging).

**Uncertainty/questions**

Q1. AR-02 / AR-05 (S-fd-h `_cleanup_close_`; S-style Destructors): PRIVATE vs SLAVE, and pinned host mounts.
- Evidence: podstorage.rs:142-146 in `bind_storage_roots`: `MountPropagationFlags::PRIVATE | MountPropagationFlags::REC`.
- Concern: a slave namespace still receives the host's unmount events. A private one keeps its own copy of every host mount, such as the install target `/var/mnt` or a loop or LUKS-backed filesystem, until the child exits. Under `run_install`'s `MountFlags=slave` (described in the test comment at lines 14-15), the child's copies used to be slaves, so a host `umount` reached them. Now it does not.
- When it matters: for short-lived `podman image ...` calls, this is harmless. It matters if a long-lived child, such as the podman service behind `pull_with_progress` → `PodmanClient::connect`, also goes through `bind_storage_roots`. That child could then keep a target filesystem busy (device-close or fs-teardown failures) after the host unmounts it.
- Why unresolved: `podman_client.rs` and the lifetime of its process are not in the packet.
- What would settle it: confirm which processes use this path and whether any of them outlives the install's unmount or teardown. If one does, `SLAVE | REC` would stop propagation back to the host just as well, while keeping host unmounts visible in the child.

Q2. AR-03 (S-interface, Independent Operation): does test 63 exercise the changed code and tell the fix apart from the old behavior?
- Evidence: test-install-shared-propagation.nu:33-35: `mount --make-rshared /` then `bootc install to-filesystem ... --source-imgref ($target_image) /var/mnt` then `if findmnt /run/bootc/storage; then ... exit 1`. The code comment (podstorage.rs:138) names `install to-existing-root`; the test uses `to-filesystem`.
- Concern: the test only distinguishes the bug if three things hold. The `to-filesystem --source-imgref` path must reach `bind_storage_roots`, presumably through `CStorage::create` → `new_podman_cmd_in`; that call site is not shown. `run_install` must run the whole script in a single namespace. And `make-rshared` on a slave mount must leave the child's copy in the same peer group as the shell that runs `findmnt`.
- Why unresolved: the install call graph and `tap.nu` are absent, and I may not run the test.
- What would settle it: show the call path from install to `CStorage`, and confirm the test fails on BASE. A passing run on HEAD alone could be explained by the path never binding at all.

Q3. AR-05 (B-state, `/etc` and `/var`): leaked state from older binaries.
- Evidence: podstorage.rs:137-141 says the old behavior "would ... stay mounted on the host's /run/bootc/storage after we exit".
- Concern: hosts that ran an older bootc may already have a stale bind on `/run/bootc/storage`. It points into a target storage root and may be stacked several times. Nothing in this change detects or removes it, and it is unclear whether later podman calls, which bind over it inside their own namespace, behave correctly when it is present.
- Why unresolved: no upgrade or recovery guidance is in the packet. Because the mount lives under `/run`, a reboot clears it, so this may be acceptable.
- What would settle it: an explicit statement that a reboot is the recovery, or a test that pre-creates a stale bind and then runs install or LBI operations.

**Testing and limitations**

Proposed tests (none were run):
- (a) Run test 63 against BASE and confirm it fails. This shows the test detects the leak (Q2).
- (b) A variant that also lists `findmnt -R /run/bootc/storage` and the target's overlay submounts after install. It would catch podman overlay mounts leaking, not just the alias bind.
- (c) If Q1 applies: start the long-lived podman service path, `umount` the target from the host namespace, and check that the backing device can be released. This distinguishes PRIVATE from SLAVE.
- (d) Cleanup in the new test is not failure-safe: an early failure leaves `/var/mnt` mounted and `setenforce 0` in place. This only matters for CI hygiene and is not an architectural defect.
