**Design summary**

When /boot sits on the same partition as /sysroot, ostree-system-generator writes boot.mount, a bind mount of /sysroot/boot onto /boot, into the normal generator directory. This is the path where /sysroot/boot/loader is a symlink and fstab has no /boot entry. Because /boot is still empty when generators run, systemd-gpt-auto-generator can claim it for the ESP. It then emits its own boot.mount, which ostree's unit overrides, and a boot.automount with an idle timeout. That automount fronts the bind mount, expires it when idle, and detaches /boot before ostree-finalize-staged.service runs at shutdown.

The PR masks boot.automount by symlinking it to /dev/null in the normal generator directory (generator.c 391-392). It also adds a booted test (privileged.rs 268-287) and wires it into tmt (tests.fmf 6).

The intended invariant, which I inferred: whenever ostree owns /boot through its generated bind mount, /boot is a plain bind mount for the whole boot. That covers idle periods and shutdown through finalization, and nothing fronts it with autofs.

Success path: the generator runs and boot.mount is written and required by local-fs.target. The boot.automount mask is written. On unit-path priority, I assume the normal generator directory outranks gpt-auto's output, which I also assume lands in the late directory. The packet does not show that. gpt-auto's automount therefore loads as masked, and /boot stays mounted.

**Uncertainty/questions**

Q1 (AR-04; S-unit Wants=/Requires=, Automatic dependencies): could masking boot.automount fail local-fs.target?
- Evidence: generator.c 391, `symlinkat ("/dev/null", normal_dir_dfd, "boot.automount")`, in boot_mount_generator.
- Why it matters: the mask is only harmless if gpt-auto pulls in boot.automount with a failure-tolerant edge (Wants=). A unit that Requires= a masked unit fails its start job. Here that unit would be local-fs.target, which can drop the system into emergency mode.
- Why the evidence is insufficient: the packet does not show which edge gpt-auto creates, or whether that differs across the systemd versions ostree supports.
- What would settle it: the gpt-auto-generator source for each supported systemd version. Alternatively, a test run on a VM where gpt-auto is known to fire that checks `systemctl is-failed local-fs.target` and `systemctl list-dependencies --reverse boot.automount`.

Q2 (AR-01; S-style Error Handling/Logging): a new abort point now sits in front of the /var mount.
- Evidence: generator.c 391-392 returns `glnx_throw_errno_prefix (error, "symlinkat(boot.automount)")`. In _ostree_impl_system_generator, lines 567-570, boot_mount_generator runs before fstab_generator.
- Why it matters: the comment at 321-323 records that an EEXIST abort here once meant "/var was never mounted at all". If any other normal-directory generator ever writes boot.automount, the same failure returns. That would follow the boot.mount link already written at 370-379.
- Why the evidence is insufficient: within the packet, fstab-generator is excluded by the fstab check at 325-329. I have no evidence on other generators, such as coreos-boot-mount-generator.
- What would settle it: the controller confirming which generators write to the normal directory on supported distros. Separately, whether a failed /boot mask should keep /var setup from running (for example, by handling EEXIST explicitly), or whether failing hard is the intended way to surface a conflict.

Q3 (AR-04; S-unit Before=/After=, BindsTo=): once the automount is gone, does shutdown ordering actually keep /boot mounted through finalization?
- Evidence: the comment at generator.c 385-386 says stopping the automount "detaches /boot underneath ostree-finalize-staged.service". The boot.mount unit at 349-362 uses `DefaultDependencies=no` with only `After=local-fs-pre.target sysroot.mount`.
- Why it matters: removing the automount removes one cause of early detach. Whether boot.mount stops before or after finalize-staged then depends on finalize-staged's own edges, such as RequiresMountsFor=/boot or After=boot.mount.
- Why the evidence is insufficient: that unit file is not in the packet.
- What would settle it: ostree-finalize-staged.service at HEAD, plus a staged-deployment reboot test that checks the new deployment actually becomes the default.

**Testing and limitations**

The new test checks two things. When FragmentPath is the generator's boot.mount, it checks that boot.automount is masked, which directly tests the generator's output. It also checks that /boot is not autofs at test time.

The autofs check only tells the bug apart from correct behaviour if gpt-auto actually fires in the tmt VM. That needs a discoverable root disk, an ESP and UEFI loader support. If the VM does not meet those conditions, this half passes both before and after the fix.

The test also does not cover the two failures the PR describes: idle expiry, and detachment during finalization at shutdown. Proposed tests:
1. On a VM where gpt-auto fires, assert that the late generator directory contains boot.automount. This proves the precondition. Then wait past the idle timeout and assert that /boot is still a bind mount from /sysroot/boot and that local-fs.target is still active. Without the mask, this fails.
2. Stage a deployment, reboot, and assert that the staged deployment booted. This catches finalize-staged running without /boot.
3. Assert `systemctl is-failed local-fs.target` returns not-failed with the mask in place. This settles Q1.
