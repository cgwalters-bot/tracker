**Design summary (intent inferred, uncertain).** The PR adds `bootc switch --target-imgref T S`. It fetches from S now and records T as the origin for future updates. S is kept as `[bootc] source-image-reference` provenance. Both are used to decide whether a repeated switch is "unchanged".

On composefs, if the fetched manifest digest equals the booted image's digest, no new deployment is made. Instead a global transaction file, `state/bootc-origin-change.json`, is written. Status reports it as a synthetic staged entry. The finalize service rewrites the booted deployment's origin at shutdown, and a generator re-arms that service on each boot.

Success path: switch → `switch_origin` → `OriginChange::new/write` → reboot → `composefs_backend_finalize` → `pending.finalize` → `write_origin` and `cancel`.

Cross-component invariants:
- (I1) At most one of "pending origin change" and "real staged deployment" controls the next boot.
- (I2) Status stays usable in every reachable boot state.
- (I3) A retry after failure keeps the requested origin.
- (I4) A recorded origin's signature mode reflects a verification that actually happened.

### Defects

**D1. A stale pending origin change makes composefs status fail, which blocks recovery** (AR-01, AR-05)

- **Evidence.**
  - `crates/lib/src/bootc_composefs/status.rs` 708–712, `get_composefs_status`: `pending.project(&amp;storage.physical_root, &amp;mut host)?;`
  - `crates/lib/src/bootc_composefs/origin.rs` 135–141, `OriginChange::validate`: `"Pending origin change no longer matches the booted image; cancel it with delete-deployment"`
  - `crates/lib/src/generator.rs` 243–256 re-arms finalization while the file exists.
  - `rollback.rs` 228 calls `get_composefs_status` before its `cancel` at 259.
- **Violated invariant.** I2: a read-only status query should not fail on a recoverable leftover from a transaction.
- **Failure scenario.**
  1. The operator stages an origin-only change for booted deployment A.
  2. At the next boot, the rollback entry B is chosen, either manually from the boot menu (the usual recovery move) or by boot-counting fallback. A's shutdown finalize may not have run, or it did not apply.
  3. The pending file persists in `/sysroot/state`.
  4. Every `get_composefs_status` call now fails because the booted verity is B, not A. That breaks `bootc status`, `upgrade`, `switch` and `rollback`. Finalization at shutdown probably fails the same way; finalize.rs context was not supplied.
  5. The only escape is `bootc delete-deployment &lt;A's verity&gt;`. The error does not show that ID, and the status command that would show it is the one failing.
- **Impact.** In the very boot state used for recovery, the management tooling stops working. The failure is reported again by every caller instead of once by its owner.
- **Scope considered.** Rejecting a stale change at finalize time is correct (`finalize` should refuse). The defect is that the read-only projection carries the same hard failure.
- **Remedy.** In `get_composefs_status`, report a mismatching pending change as stale (a warning or a status field) and skip the projection. Let `rollback`, `upgrade` and `switch` cancel stale changes. Include the deployment ID in the message.
- **Distinguishing test.** A unit fixture writes a pending change for verity A while the booted verity is B. Assert that status succeeds without a staged entry, and that `bootc rollback` or `switch` can clear it. Current code fails at `project`.
- **Source.** S-style "Error Handling", "Logging"; O-rollback "Manual rollbacks".

**D2. `do_upgrade` and `composefs_rollback` cancel the pending change before their own commit point** (AR-05)

- **Evidence.**
  - `crates/lib/src/bootc_composefs/update.rs` 386, `do_upgrade`: `super::origin::cancel(&amp;storage.physical_root)?;` runs before `primary_boot_entry` (388), boot setup, and `write_composefs_state` (476–483).
  - `rollback.rs` 259 cancels before the rollback itself is performed.
- **Violated invariant.** I1 and I3: the replacement state should become durable before the state it supersedes is discarded.
- **Failure scenario.**
  1. A pending change to T exists. `bootc upgrade` pulls from T, because the projected `host.spec.image` is T (origin.rs 176).
  2. The pull succeeds and the pending file is removed and fsynced.
  3. Boot-entry setup or state writing then fails, for example ESP full or I/O error.
  4. No new staged deployment exists and the booted origin is still the old one.
  5. A retried `bootc upgrade` silently pulls from the old origin, so the operator's recorded intent is lost. A failed `bootc rollback` after line 259 loses the pending change in the same way.
- **Impact.** Retry is not idempotent, and after an error the update source switches without notice. This matters for the offline/technician workflow the docs target.
- **Scope considered.** The early cancel probably exists because `composefs_backend_finalize` checks the pending file before the real staged deployment (finalize.rs 96–97). If the file were left in place after staging, finalize would pick the wrong transaction. So the ordering problem is in which transaction finalize gives precedence to, and moving `cancel` alone is not enough.
- **Remedy.** Have finalize and validation treat a real staged deployment whose verity differs from the pending one as superseding it. Then cancel only after `write_composefs_state` (or the rollback swap) has succeeded.
- **Distinguishing test.** Inject a failure between update.rs 386 and 476 (for example, a read-only state dir for `write_composefs_state`). Assert that the pending file still exists and that status still reports origin T. Current code removes it.
- **Source.** O-upgrade "Atomically swapping boot configuration"; B-state "/var".

### Uncertainty and questions

**Q1. A download-only pending change makes the shutdown finalize fail** (AR-01)

- **Evidence.** `origin.rs` 182–185 `finalize`: `ensure!(!self.finalization_locked, "Pending origin change is download-only")`. finalize.rs 96–97 returns that result. `switch_origin` starts the finalize service even when locked (switch.rs 245). The generator re-arms "even locked changes" (generator.rs 250). The unit test at origin.rs 285 asserts that this case returns an error.
- **Why unsettled.** finalize.rs before line 93 was omitted. If the existing locked-staged check returns `Ok` before line 96, this is fine. Otherwise, every shutdown while locked logs the expected "locked" condition as a finalize failure.
- **What would settle it.** The full finalize.rs, plus a test that a locked pending change makes finalize return `Ok` with only debug logging.
- **Source.** S-style "Logging".

**Q2. The ostree backend records a signature-enforcing origin for T without verifying T** (AR-06)

- **Evidence.** `cli.rs` 1705–1706: `sigverify = sigpolicy_from_opt(opts.enforce_container_sigpolicy)` is applied to the target. `deploy.rs` 569–575 `set_image_reference` assigns S's commit to T's ref without fetching. Composefs explicitly rejects this combination (switch.rs 51–54), but ostree does not.
- **Scenario.** The actor is whoever controls the "technician's temporary registry" or local storage, as in the documented example. They control the content of S. The privileged action is staging that content as root while the deployment is labeled with T and the container-policy mode. The outcome is that status shows a policy-verified T origin, but S was checked only under its own scope's policy.
- **Why unsettled.** It is unclear whether ostree-ext re-verifies or relabels the deployment, and what the intended trust contract is.
- **What would settle it.** A statement of intent, plus a test with a policy that rejects S's scope and accepts T's.
- **Source.** C-design "Filesystem integrity".

**Q3. The synthetic staged entry has the same verity as booted** (AR-03)

- **Evidence.** `origin.rs` 168–177 `project` clones the booted entry into `host.status.staged`. rollback.rs 229–233 and update.rs 330–336 then have to undo that locally.
- **Why unsettled.** `bootc status --json` is a machine interface. Other callers of `get_composefs_status` (gc, soft-reboot checks, external tools) may assume staged and booted are different deployments. Those callers were not supplied.
- **What would settle it.** A list of the callers and a documented contract for the status JSON.
- **Source.** S-interface "Interface Portability and Stability Promise".

**Q4. The image ref for T is written immediately and never rolled back** (AR-05)

- **Evidence.** `deploy.rs` 569–575 and 755–761 call `set_ref_immediate` for T before staging.
- **Risk.** If staging fails afterwards, T's existing ref is overwritten to point at S's commit. Possible effects are cache confusion or keeping that commit alive.
- **What would settle it.** The ostree-ext GC and cache semantics for image refs (store.rs omitted).
- **Source.** O-upgrade "Assembling a new deployment directory".
